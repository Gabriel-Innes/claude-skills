# Common mistakes when reading Acumatica through OData

Use as a review checklist for OData consumers (BI tools, Power Query, sync jobs). Grep the request, Power Query M or
code for the pattern in "Looks like", then apply the rule.

| # | Looks like | Why it is wrong | Rule (source) |
|---|---|---|---|
| 1 | `PUT` / `POST` / `PATCH` / `DELETE` to `/api/odata/...` | Both OData interfaces are read-only. Writes go through the REST API (`references/rest/`). | I300 *OData Endpoints*; *Accessing DACs Through OData* |
| 2 | `/odata/dac/SOOrder` without `/t/<TenantName>/`, or the tenant appended to the username | 2026 R2 URLs are `<instance>/t/<TenantName>/api/odata/dac` and `.../gi`; the tenant is the login name from Tenant List (SM203530), spaces as `%20`; the username carries no tenant suffix. The 2024 R1 shapes are `/OData/<Tenant>` (3.0) and `/ODatav4/<Tenant>` (4.0), tenant optional on single-tenant instances; `/odatav4/<Tenant>` still answers on a clean 2026 R2 instance as an alias of `/t/<Tenant>/api/odata/dac` (owner-verified), so do not flag it as broken, only as undocumented. | *DAC-Based OData: General Information*; *... in Microsoft Excel*; I300 Examples 1.1.1, 1.1.2; owner test 2026-10-06 |
| 3 | Treating `/OData/` (inquiry) requests as OData 4.0 on an older release, or `datetime'...'` literals on 2026 R2 | 2024 R1 documents the inquiry endpoint as OData **3.0** (`odata.metadata` key, `$format=json`, `datetime'...'`); 2026 R2 documents `/api/odata/gi` as OData 4.0 with bare literals. Probe `$metadata` and read its `edmx` version. | I300 Example 1.1.1; *Generic Inquiries and OData: General Information* |
| 4 | Polling `/api/odata/gi/<Inquiry>` for an inquiry that has parameters | The entity set does not bind parameters and can return an empty result without an error; call `<Title>_WithParameters(Param='value')` (or `(Param=@1)?@1='value'`). | *Generic Inquiry Access Through OData: Data Retrieval* |
| 5 | `$expand=` or `$count` on an inquiry-based URL | Not supported by the inquiry-based interface, nor is `IsOf()`. Build one inquiry per detail kind, or use the DAC-based interface. | *Generic Inquiries and OData: Preparation of an Inquiry for Exposure* |
| 6 | Reading an empty 200 response as "no rows" | For inquiries, 200 with **no body** signals an unsupported query (for example filtering or sorting on a formula column); an empty result is `{"value": []}`. | *... Data Retrieval*; *... Preparation of an Inquiry for Exposure* |
| 7 | `$filter=NoteText eq ...` or `$select=...,DocBal` on a DAC | Fields in the entity set's `Cap.FilterRestrictions` `NonFilterableProperties` are refused in **both** `$filter` and `$select`; `Filterable=false` bars every field declared in that DAC (inherited fields allowed). Check `metadata/entity-sets.md`. | *DAC-Based OData: General Information*, *Basic Data Retrieval*, *Filtering Records* |
| 8 | `$filter=ItemStatus eq 'Active'` on `InventoryItem` | DAC filters use the **stored value** (`'AC'`); inquiry filters use the displayed value (`'Active'`). Element Inspector's Drop-Down Values lists both. | *DAC-Based OData: To Filter the Requested Data*; *... To Filter the Results of a Generic Inquiry*; *DAC Discovery: General Information* |
| 9 | `$filter=InventoryID eq 'AALEGO500'` on `INSiteStatus` | DAC foreign keys are integer IDs (`InventoryID eq 41`); the code lives on the related DAC (`$expand=InventoryItemByInventoryID($select=InventoryCD)`), and filtering on a related field uses the navigation path (`Nav/Field eq ...`). Check the field's Edm type in the snapshot. | *... $expand, $select, and $filter Parameters*; *Filtering Records* |
| 10 | `$filter=SOLineCollection/InventoryID eq 1` | Collections are filtered with lambdas: `SOLineCollection/Any(x: x/InventoryID eq 1)`, `All(...)`, or `SOLineCollection/$count eq 3`. | *DAC-Based OData: Filtering Records* |
| 11 | `$expand=A($expand=B($expand=C($expand=D)))` | Expansion depth is 3 by default; raise `maxExpansionDepth` on the `odata` element in `Web.config` or flatten the query. | *DAC-Based OData: Basic Data Retrieval* |
| 12 | `$top`/`$skip` paging without `$orderby` | The documented pattern adds `$orderby`; without it the server orders by key fields ascending, which is fine only if that is what the page boundaries assume. | *Basic Data Retrieval*; *... Data Retrieval* |
| 13 | `$apply=groupby(...)` or `aggregate(...)` | The OData aggregation extension is not supported; aggregate client-side or build an inquiry. | *DAC-Based OData: General Information*; I300 Example 3.1.2 |
| 14 | Delta sync on `LastModifiedDateTime` only | Deletions are invisible to a modified-date filter. Add the DAC on Tables to Track Deleted Records (SM207010) and read `<DAC>/px.GetDeletedRecords()?$filter=DeleteDate ge ...`; send `PX-ApiDeleted: SHOW` to see soft-deleted rows, `PX-ApiArchive: SHOW` for archived ones. | *DAC-Based OData: Retrieving Archived and Removed Records* |
| 15 | `2024-11-01T00:00:00+03:00` unencoded in a URL | `+` must be sent as `%2b` in a query string; `Z` or a negative offset needs no encoding. | *Retrieving Archived and Removed Records*; I300 Example 3.1.2 |
| 16 | Sizing the API-user licence for OData basic-auth clients | Basic-auth OData sign-ins count as **conventional users** (Concurrent Users on License Monitoring Console (SM604000)), not API users; OAuth sessions count as API users. | *DAC-Based OData: General Information*; I300 Appendix A |
| 17 | Giving a BI account `Administrator` because OData "returned nothing" | Inquiry-based reads need **View Only** on the inquiry (Hidden node when it has no workspace); the `BI` role covers the predefined `BI-*` inquiries and `OData4 User` covers DAC-based access; the DAC interface shows what the UI rights show. | *... To Expose Inquiry Results Through OData*; *User Roles: Predefined Roles* |
| 18 | Expecting the inquiry's grid columns only | Inquiry metadata also publishes the source tables' key fields even when they are not in the results grid; names are generated from English captions (spaces removed, leading digit prefixed with `_`, duplicates suffixed `_2`). | *Generic Inquiry Access Through OData: General Information*; *... Preparation of an Inquiry for Exposure* |
| 19 | Parsing `QtyOnHand` as a number from an inquiry response, or `odata.metadata` as `@odata.context` | The inquiry examples print decimals as strings and the key `odata.metadata`; DAC responses print JSON numbers and `@odata.context`. Parse defensively. | *... with Parameters*, *... To Filter the Results ...*; *DAC-Based OData: Basic Data Retrieval* |
| 20 | Naming a DAC or field that is not in `metadata/` and not on the client's `$metadata` | A clean 2026 R2 snapshot is bundled; a client's instance differs by modules, customizations and user-defined fields. Verify on the client's `/api/odata/dac/$metadata` or with Element Inspector. | `metadata/INDEX.md`; *DAC Discovery: General Information* |
| 21 | Opening CORS to `*` in production because "it did not work" | CORS is already on for all origins by default; browser clients need the four OData headers in `exposedHeaders`. Restrict `origins` instead; saving `Web.config` restarts the site. | *To Configure CORS* |
| 22 | Reading `Customer` fields from the `Customer` entry only | Derived DACs list only added fields; `PX.Objects.AR.Customer` inherits key and most fields from `PX.Objects.CR.BAccount` (`BaseType` column in `metadata/api/INDEX.md`). | bundled snapshot |
