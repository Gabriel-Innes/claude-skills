# Cin7 Core API references index

Extraction of the **Cin7 Core** (formerly DEAR Inventory) API v2 developer portal. Read `api-basics.md` first
for the protocol, then open only the group file the request needs. The group files, `endpoints.md` and
`enums.md` are generated by `scripts/build_core_api_reference.py` from the portal's API Blueprint export; the
two hand-written files curate the portal's rules. Nothing here covers **Cin7 Omni**.

## Looking things up

Grep; never read `groups/production.md`, `groups/purchase.md` or `groups/sale.md` whole (5,000 to 6,000 lines each).

| Question | Where |
|---|---|
| Does the endpoint exist, what is its exact path and method | `endpoints.md`: grep the path (`/sale/invoice`), a word of the resource (`Stock Take`) or the method column (`^\| DELETE`) |
| Which query parameters does a GET take | `endpoints.md` Parameters column, then the action's `Parameters:` list in the group file |
| The fields of a document and which are required or read-only | the `### Available Fields for ...` table in the group file: grep `` `FieldName` `` or `Available Fields for Sale Invoice` |
| Allowed values of a field | the field's Notes column, or the linked anchor in `enums.md` (`SaleStatesList`, `webhookTypeValues`) |
| The shape of a request or response body | the action in the group file: `<a id="post-sale-invoice">` then the ```json fences under `Request body:` / `Response 200:` |
| The statuses a POST/PUT requires | the bullet notes directly under the action heading in the group file (`will return exception if`) |
| What a status value means | `enums.md`, e.g. `^\|\`BACKORDERED\`` |
| Which sub-model a line array uses | the field's type column links an anchor (`SaleOrderLineModel`), defined in `groups/other-models.md` or the same group file |
| Webhook event names and payloads | `groups/webhooks.md` (type table and "Webhooks payload examples") |

## Known limits of these references

- **One snapshot, no version stamp.** The portal states no release number or edition date; "verified" is the
  download date. The API is `v2`; the portal links a separate "previous API version" that is not bundled.
- **Cin7 Core only.** Cin7 Omni has its own API and is not covered; answer Omni questions with the scaffold
  caveat (`SKILL.md` § 1).
- **The portal contradicts itself in places**, and the files reproduce it as written: the introduction names
  seven paginated endpoints while 47 GET actions document `Page`/`Limit`; the CRM group's GET headings for *Task
  Category* and *Workflow* show the path `/crm/task` while their POST/PUT use `/crm/taskcategory` and
  `/crm/workflow`; the `Purchase List` field table swaps the descriptions of `UnstockStatus` and
  `InvoiceStatus`; `Customer` on the `Sale List` table is typed `Date`; the notes on `/advanced-purchase/stock`
  say both that a Simple Purchase is converted to Advanced on POST/PUT and that the endpoint applies only to
  Advanced Purchases with "Use Put Away" enabled. Flag such rows as "to confirm on the account".
- **38 example bodies are not valid JSON as written** (hand-typed in the portal: unquoted keys, trailing
  commas); they are kept verbatim. Field tables, not examples, are the authority on names.
- **Sample identifiers in examples** (GUIDs, order numbers, names, e-mail addresses) are the portal's own sample
  data, not real accounts; the portal's sample `api-auth-*` header values are never written.
- **No rate-limit detail** beyond the 60-calls-per-minute line, no error-message catalogue, no field-level
  validation messages, no OAuth: say so rather than guess.
- **Webhook payload examples** are kept in the portal's own list form (`+ Sale/Created Response 200 ...`) rather
  than fenced, because each example is a named variant of one response.
